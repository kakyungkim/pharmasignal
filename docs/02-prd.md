## 1. 문제 정의

제약사의 안전성·경쟁 정보 담당자는 매일 흩어진 출처를 손으로 훑음. 임상시험 등록(ClinicalTrials.gov), 규제 공시, 전문지 기사, 문헌이 각각 다른 형식으로 갱신되고, 상당수 사이트가 봇 차단과 지역 제한을 걸어 두어 자동 수집도 쉽지 않음.

여기에 더 큰 벽이 있음. 사내 임상 문서와 피험자 관련 텍스트는 규제와 계약상 외부 상용 API로 보낼 수 없어, 공개 정보 분석을 자동화해도 **정작 중요한 내부 데이터는 LLM을 못 쓰는 상태**로 남음. 제약과 의료에서 AI 도입이 막히는 실제 이유가 성능이 아니라 이 데이터 반출 제약임.

## 2. 목표와 비목표

**목표**
- 주제어 하나로 공개 임상시험·규제 데이터를 수집해 경쟁 지형을 요약함
- 분석 코드를 모델이 직접 작성하고, 사람이 손대지 않아도 격리 환경에서 실행함
- 반출 금지 텍스트를 상용 API에 보내지 않고 자체 GPU에서 처리하는 경로를 실제로 갖춤

**비목표 (해커톤 범위 밖)**
- 인과성 평가나 규제 제출용 판단. 이 도구는 초안 정리까지만 하고 판단은 사람이 함
- 사내 임상 데이터베이스 연동, 인증·권한 체계
- 웹 UI. 이번 범위는 CLI와 구조화 출력까지

## 3. 사용자

| 사용자 | 상황 | 이 도구로 얻는 것 |
|---|---|---|
| 안전성(PV) 담당 | 매일 공시와 문헌에서 이상반응 신호를 찾음 | 수집·정리를 자동화해 판단에 시간을 씀 |
| 경쟁정보(CI) 담당 | 경쟁 파이프라인 변화를 추적 | 임상단계·스폰서 분포를 주기적으로 받음 |
| 데이터 담당 | 위 두 요청을 스크립트로 받아 처리 | 요청마다 코드를 새로 짜지 않아도 됨 |

## 4. 사용자 스토리

- PV 담당으로서, 주제어를 넣으면 최근 임상시험 현황과 단계별 분포를 표로 받고 싶음. 매일 사이트를 훑는 시간을 줄이기 위함.
- CI 담당으로서, 어떤 스폰서가 해당 계열에 얼마나 투자하는지 순위로 보고 싶음. 경쟁 동향 보고서 초안을 빨리 쓰기 위함.
- 데이터 담당으로서, 새로운 분석 요청이 와도 코드를 직접 짜지 않고 모델이 작성한 코드가 안전하게 실행되기를 바람.
- 규제 담당으로서, 내부 문서를 요약할 때 그 텍스트가 외부 상용 API로 나가지 않는다는 것이 기술적으로 보장되기를 바람.

## 5. 기능 요구사항

| ID | 요구사항 | 검증 |
|---|---|---|
| FR-1 | 주제어를 인자로 받으면 시스템은 공개 임상시험 레코드를 수집하여 정규 스키마로 반환해야 함 | 25건 수집, 필드 누락 없음 |
| FR-2 | 한 Bright Data 제품이 막히면 시스템은 다른 제품 경로로 넘어가야 함 | Web Unlocker → 프록시 → 직접 호출 순 확인 |
| FR-2b | 이상사례 논의가 오가는 문헌은 검색으로 찾아야 함 | SERP API로 신호 후보 6건 수집 (**확인 완료**) |
| FR-3 | 수집 결과가 주어지면 시스템은 그 데이터를 분석하는 Python 코드를 LLM으로 생성해야 함 | 생성 코드가 문법 오류 없이 실행 |
| FR-4 | 생성된 코드는 로컬이 아닌 격리 샌드박스에서 실행되어야 함 | 샌드박스 실행 로그 확인 |
| FR-5 | 민감 표시가 된 텍스트는 상용 API가 아닌 자체 배포 모델로만 추론되어야 함 | 요청이 자체 엔드포인트로만 나감 |
| FR-6 | 어느 단계가 실패해도 파이프라인은 중단되지 않고 폴백으로 완주해야 함 | 키 0개 상태에서 완주 (**확인 완료**) |
| FR-7 | 실행 출력의 집계는 고정 로직으로 다시 구해 대조해야 함 | 11개 항목 대조, 전부 일치 (**확인 완료**) |
| FR-8 | 매 실행은 단계별 제공자와 대조 결과를 파일로 남겨야 함 | `docs/evidence/run-<주제>.json` 생성 (**확인 완료**) |

## 6. 데이터 모델

```
Trial                                Signal
  nct      str   NCT 식별자            title  str   문헌·기사 제목
  title    str   시험 제목             link   str   출처 주소
  status   str   RECRUITING / ...      kind   str   web | scholar
  phase    str   PHASE1~4 / NA
  sponsor  str   주관 기관           CrossCheck
  start    str   시작일 (ISO)          checked/agreed  int  대조한 값과 일치한 값
                                       mismatches     list 어긋난 항목
```

수집 소스가 늘어나도 이 스키마로 정규화해서 하위 단계가 소스에 의존하지 않게 함.

## 7. 아키텍처

네 플랫폼이 각각 대체 불가능한 역할을 맡음.

| 단계 | 플랫폼 | 역할 | 빼면 안 되는 것 |
|---|---|---|---|
| 수집 | Bright Data | 등록 데이터 확보와 이상사례 문헌 검색 | 봇 차단 사이트 접근 |
| 판단 | Qwen Cloud | 구조화 추출, 분석 코드 생성 | 긴 문서 추론 |
| 실행 | Daytona | 생성 코드를 격리 실행 | 모델이 쓴 코드의 안전한 실행 |
| 대조 | (고정 로직) | 실행 출력의 집계를 다시 구해 대조 | 판정을 모델에게 맡기지 않음 |
| 반출 금지 | Nosana | 반출 금지 텍스트 추론 | 데이터가 외부로 나가지 않음 |

Bright Data는 계정에 열려 있는 제품에 따라 Web Unlocker, SERP API, 프록시 가운데 하나를
고른다. 한 제품이 막혀도 그 스폰서를 통째로 포기하지 않는다.

각 단계는 인터페이스(Protocol)로 정의되고 구현이 갈아 끼워짐. 키가 없거나 호출이 실패하면 같은 인터페이스의 폴백 구현이 대신 동작하므로, 데모 중 한 플랫폼이 죽어도 파이프라인은 완주함.

## 8. 비기능 요구사항

- **완주 보장.** 외부 의존이 모두 실패해도 종료 코드 0으로 끝나야 함. 발표 중 와이파이 상태에 데모가 좌우되면 안 됨.
- **비밀 관리.** 키는 `.env`로만 주입하고 저장소에 올리지 않음. 로그에 키를 출력하지 않음.
- **응답 시간.** 전체 파이프라인 2분 이내. 발표 시간이 짧음.
- **관측 가능성.** 각 단계가 실제 경로인지 폴백인지 화면에 명시함. 심사위원이 무엇이 진짜인지 확인할 수 있어야 함.
