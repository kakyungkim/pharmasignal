# 08. 해커톤 이후 업데이트

> 2026-08-22 행사 종료 후 적용. 다른 팀의 발표에서 배운 것을 실제 코드와 문서에 반영한 기록이다.
> 팀별 관찰은 [07-teams.md](07-teams.md), 결과 회고는 `memory/hackathon-outcome.md`.

무엇을 바꿨고 왜 바꿨는지를 한곳에 모은다. 회고가 문서로만 남고 코드가 그대로면 배운 것이 아니다.

---

## 1. 한 스폰서에서 제품을 여러 개 쓴다

**무엇을 봤나.** 한 팀은 Bright Data에서 SERP API와 Scraping Browser 두 제품을 함께 붙이고 저장소에 "제품 2종을 쓴다"고 명시했다. 심사 기준이 "More sponsor APIs integrated = higher score"였으니 개수에 정확히 맞춘 것이다.

**우리는 무엇을 했나.** Web Unlocker zone 하나에 막히자 프록시로 방향을 틀었고, 그것도 카드 등록을 요구해 Bright Data를 통째로 0으로 뒀다. **제품이 여러 개라는 것을 다시 확인하지 않았다.**

**무엇을 바꿨나.** `providers/collectors.py`에 `BrightDataSerpCollector`를 추가했다. Web Unlocker와 같은 `api.brightdata.com/request` 엔드포인트를 쓰되 zone만 다르다. `build_collector()`가 이제 세 갈래를 순서대로 시도한다.

```
Web Unlocker → SERP API → 프록시 → 직접 호출(폴백)
```

계정에 어떤 제품이 열려 있든 하나만 걸리면 그 스폰서가 살아난다. 설정은 `BD_ZONE`과 `BD_SERP_ZONE`으로 나눴다.

## 2. 단계 이름을 사용자의 행동으로

**무엇을 봤나.** 상위 팀의 단계 이름이 전부 사용자가 하는 일이었다.

| 팀 | 단계 이름 |
|---|---|
| ReviewForge | READ · SEE · CREATE · VERIFY |
| Job2Test | Eyes · Brain · Hands |
| Salesman | Catch · Draft · Approve · Close |

**우리는 무엇을 했나.** 수집, 판단, 실행, 반출 금지였다. 앞의 셋은 시스템의 동작이고 넷째는 개념이라 **사용자가 하는 일이 하나도 없었다.**

**무엇을 바꿨나.** 찾기, 읽기, 따지기, 가두기로 바꿔 봤다가 **되돌렸다.**

찾기와 읽기는 무엇을 하는 단계인지 오히려 흐려지고, 따지기와 가두기는 구어체라
제약 도메인 문서에 맞지 않았다. 남의 팀에서 통한 방식이 우리 도메인에도 통하는 것은
아니었다. 단계 이름은 수집, 판단, 실행, 반출 금지로 유지한다.

다만 각 단계가 무엇을 하는지는 한 줄씩 붙여 두었다. 이름을 갈아 끼우는 것보다
설명을 붙이는 편이 이 문서에는 맞는다.

**남은 과제.** 사용자의 행동으로 부르는 것이 전달에 유리하다는 관찰 자체는 유효하다.
발표 자료처럼 처음 보는 사람을 상대하는 자리에서는 다시 검토할 것.

## 3. 생성물은 코드가 검사한다

**무엇을 봤나.** 세 팀이 같은 구조에 독립적으로 도달했다. 정답 검증(3팀), 정책 린트(5팀),
규칙 검사(1팀)로 형태는 달랐지만 원리는 하나다. **생성은 LLM이 하고 검사는 코드가 한다.**
한 팀은 "판정을 LLM에게 맡기지 않는다"고 아예 못 박고 `exit_code == 0`만을 통과 기준으로 삼았다.

**우리는 무엇을 했나.** Qwen이 분석 코드를 쓰고 Daytona가 실행했지만, **나온 숫자가 맞는지는
아무도 따지지 않았다.** 모델이 잘못된 집계를 짜면 그대로 화면에 찍혔다. 우리가 이 원리를
`demo-verifier` 에이전트라는 개발 규율로는 갖고 있었으면서 제품 안에는 넣지 않았다.

**무엇을 바꿨나.** `verify.py`를 추가하고 파이프라인에 대조 단계를 넣었다. 같은 집계를
고정 로직으로 다시 구해 실행 출력과 대조하고, 어긋나면 어긋난 항목을 그대로 표시한다.

```
[대조] 생성된 집계를 고정 로직으로 다시 계산
  11/11 일치
```

붙이자마자 실제로 걸렸다. 첫 실행에서 불일치 1건이 떴는데 확인해 보니 대조 로직의 파서
문제였다. `RECRUITING`이 `ACTIVE_NOT_RECRUITING` 안에서 잡히고 있었다. 앞에 다른 글자가
붙은 경우를 건너뛰도록 고쳤고 회귀 테스트 4개를 붙였다.

## 4. 실행 원장을 파일로 남긴다

**무엇을 봤나.** 한 팀은 단계마다 상태와 소요 시간을 행으로 쌓아 두고 승자를 모델이 아니라
그 기록으로 골랐다. "실행 영수증"이라는 표현을 썼다.

**우리는 무엇을 했나.** 실행이 끝나면 화면에 표를 찍고 끝이었다. 발표가 끝나면 아무것도
남지 않았고 "그때 진짜 돌았다"를 증명할 것이 캡처뿐이었다.

**무엇을 바꿨나.** `ledger.py`를 추가해 매 실행을 `docs/evidence/run-<주제>.json`으로 남긴다.
어느 단계가 어느 제공자로 돌았고 폴백이었는지, 대조 결과가 어땠는지, 총 몇 초 걸렸는지가
들어간다. 나중에 다시 열어 볼 수 있고 여러 번 돌린 결과를 견줄 수도 있다.

## 5. 스폰서 표에 "필수성"을 적는다

**무엇을 봤나.** 한 팀은 스폰서 표에 열을 하나 더 두고 플랫폼마다 없으면 왜 안 되는지를 한 문장으로 적었다. Daytona 칸에는 "없으면 프로젝트가 성립하지 않는다"라고 썼다.

**우리는 무엇을 했나.** 같은 논리를 갖고 있었지만 발표 서사로만 풀었고 표로 만들지 않았다. 평가자가 점수를 매길 때 근거로 삼을 형태가 아니었다.

**무엇을 바꿨나.** README의 파이프라인 표에 필수성 열을 넣었다. 아래 6번 항목과 함께 적용했다.

## 6. 주장은 매핑으로, 한계는 주석으로

**무엇을 봤나.** 2위 팀은 플랫폼 매핑 표를 앞세우고 "현장 실제 호출 0/4"을 그 옆 작은 글씨로 달았다.

**우리는 무엇을 했나.** 4단계 요약표를 앞세웠는데 그 표의 한 줄이 "폴백"이었다. 실호출은 우리가 셋, 저쪽이 0인데 1차 관문에서 우리가 걸렸다.

**정직함은 양쪽 다 지켰다.** 갈린 것은 결함을 채점되는 축 위의 한 줄로 만들었느냐다. 숨기라는 뜻은 아니고 배치의 문제다.

**무엇을 바꿨나.** README에서 플랫폼 매핑을 앞세우고, 실호출 현황은 그 아래 별도 줄로 정확히 적는다. 실행 화면의 요약표는 그대로 둔다. 데모를 보는 사람에게는 그 표가 정직함의 증거이기 때문이다.

## 7. 데모 영상을 만든다

**무엇을 봤나.** 통과한 팀 저장소에 `video/demo.mp4`와 녹화 스크립트가 함께 있었다.

**우리는 무엇을 했나.** 정적 슬라이드만 냈다. 1차 관문이 제출 파일 심사였으니 라이브 데모의 설득력이 전달될 자리가 없었다.

**무엇을 바꿨나.** `scripts/record_demo.py`를 추가하고 **실제로 영상을 만들었다**(`video/demo.mp4`, 28초).

화면 녹화는 권한과 창 배치가 필요해 자동화가 어렵다. 대신 파이프라인을 실제로 돌려
그 출력을 받아 터미널처럼 한 줄씩 흘러가는 화면으로 렌더한다. 꾸며낸 화면이 아니라
실행 결과 그대로다. 한글 고정폭 폰트(D2Coding)를 써서 표 정렬이 어긋나지 않는다.

주제를 바꿔 다시 돌리면 영상도 새로 만들어진다.

```bash
python scripts/record_demo.py "antibody-drug conjugate" 20
```

## 반영하지 않은 것

**게이트와 테스트를 줄이지 않았다.** 완성도가 선정의 결정적 요인이 아니었다는 것은 확인됐지만(미완성이라 밝힌 팀이 3위를 했다), 그렇다고 검증을 줄이는 것은 다른 문제다. 게이트 4/4와 테스트 14개는 그대로 둔다.

**주제를 바꾸지 않았다.** 도메인 접근성이 약점이었던 것은 맞으나, 주제를 대중적인 것으로 갈아타면 이 프로젝트가 가진 유일한 강점인 실무 근거가 사라진다. 대신 **첫 화면에서 도메인 지식 없이도 문제가 보이게 하는 것**을 다음 과제로 둔다.
