## 1팀 · ReviewForge

**발표자:** Minjoo Suh
**한 줄:** From local campaign application to verified review, one AI agent workflow.
**데모:** https://reviewforge-agentforge-seoul.vercel.app/
**테스트용 공고:** https://xn--939au0g4vj8sq.net/cp/?id=2270126
**발표 자료:** `presentation/ReviewForge_AgentForge_presentation.pdf` (6장)

> 발표 뒤 본인이 채팅방에 데모 링크와 자료를 공유하며 "발표에서 동기와 구현 기능을
> 충분히 설명하지 못한 것 같아 덧붙인다"고 밝혔다. 아래는 그 자료와 데모를 직접 확인한 내용.

### 들은 내용과 자료로 확인한 것

체험단 광고를 매번 읽고 파악해야 하는데 업체마다 조건이 달라 일일이 확인하는 것이 번거로웠다.
자료의 문구로는 **"I kept repeating the same work every time I applied."**

**흐름은 APPLY → VISIT → WRITE → VERIFY.** 공고 URL 하나를 붙여넣으면 제공 내역과 방문 조건,
후기 미션을 가져와 그 캠페인에 맞는 신청 문구를 만든다. 방문 뒤에는 사진과 실제 메모를 올리면
후기를 생성하고, 키워드 수와 글자 수, 미디어 개수 같은 캠페인 규칙을 검사한다.

데모에서 확인한 입출력은 이렇다. 입력은 **캠페인 URL과 본인 강점**(쉼표 구분, 500자 이내),
출력은 **신청 문구 3종**이다.

**네 플랫폼을 제품 단계에 하나씩 대응시켰다.** 자료 5장의 제목이
"Every sponsor tool is mapped to a real product step."

| 단계 | 플랫폼 | 하는 일 |
|---|---|---|
| 01 READ | Bright Data | 공개 공고 페이지에서 제공 내역, 방문 조건, 후기 미션 수집 |
| 02 SEE | Nosana | 업로드한 방문 사진을 GPU 추론으로 분석·분류 |
| 03 CREATE | Qwen Cloud | 캠페인 규칙 구조화, 신청 문구와 제목, 후기, 사진 순서 생성 |
| 04 VERIFY | Daytona | 키워드 수, 글자 길이, 미디어 개수, 필수 링크를 **고정 로직으로** 검사 |

두 경로가 나뉜다. 신청은 Bright Data → Qwen Cloud, 후기 작성은 Bright Data → Nosana →
Qwen Cloud → Daytona.

마지막 장의 요약은 **READ → UNDERSTAND → CREATE → VERIFY**이고,
"ReviewForge is not another AI writing tool."로 못 박았다.

### 분석

**심사위원에게 체험단을 먼저 설명했다.** 자료 2장이 "What is a blog experience campaign?"이다.
안다고 가정하지 않고 리뷰어가 얻는 것과 지역 상점이 얻는 것을 나눠 보여줬다. 처음에 나는 이 팀이
"설명이 필요 없는 주제를 골랐다"고 봤는데 **정확하지 않다. 설명이 필요한 것을 알고 한 장을 썼다.**
우리는 제약 규제를 설명 없이 전제로 깔았다. 차이는 주제의 난이도가 아니라 **설명을 준비했느냐**였다.

**아픈 지점은 문제 정의다.** 자료 3장 제목이 "The real pain is not just writing.
It is everything around it." 글쓰기만 자동화하는 도구는 이미 많으니, 그 앞뒤의 공고 읽기,
신청, 규칙 검사를 문제로 잡았다. 경쟁 도구와의 차이를 문제 정의 단계에서 미리 갈랐다.

**Daytona를 LLM이 아니라 고정 로직 실행에 썼다.** 키워드가 몇 번 나왔는지, 글자 수가 맞는지,
사진이 몇 장인지는 모델이 셀 일이 아니다. **생성은 Qwen이 하고 검사는 코드가 한다.**
우리가 내부 규율로 삼은 "만든 쪽과 검수하는 쪽을 나눈다"를 이 팀은 제품 안에 넣었다.
2팀의 "실행으로 검증한다"와 같은 계열이다.

**Nosana를 이미지에 썼다.** 업로드한 사진을 GPU로 분석·분류한다. GPU가 필요한 이유가
설명 없이 성립한다. 우리는 텍스트 추론에 1.5B 모델을 썼는데, 그건 "왜 GPU가 필요한가"를
규제 맥락으로 설명해야 했다.

**범위를 스스로 잘랐다.** "Focused on local, in-person experiences — product-shipping
campaigns are outside this MVP." 배송형 체험단을 뺀다고 명시했다. 못 한 것이 아니라
안 한 것이라고 밝히면 완성도가 오히려 올라간다.

**초기 분석의 오류 정정.** 나는 처음에 "플랫폼 하나를 깊게 썼다"고 적었으나 사실이 아니다.
**네 개를 다 썼고, 각각을 제품 단계에 대응시켜 슬라이드 한 장으로 보여줬다.**
구조는 우리와 같았다. 갈린 것은 단계 이름이 사용자의 행동(READ, SEE, CREATE, VERIFY)이었고
우리는 기술 동작(수집, 판단, 실행)과 개념(반출 금지)이었다는 점이다.

### 우리와의 대비

| | ReviewForge | PharmaSignal |
|---|---|---|
| 낯선 개념 | 한 장을 써서 설명 | 설명 없이 전제 |
| 문제 정의 | 글쓰기가 아니라 그 주변 | 흩어진 출처 수집 |
| 단계 이름 | READ, SEE, CREATE, VERIFY | 수집, 판단, 실행, 반출 금지 |
| Daytona 용도 | 규칙 검사(고정 로직) | 생성 코드 실행 |
| Nosana 용도 | 사진 분석·분류 | 텍스트 추론 |
| 범위 | 스스로 잘라내고 명시 | 잘라낸 것을 명시하지 않음 |
| 배포 | Vercel에 공개 | 로컬 CLI |

## 2팀 · Does it actually run?

### 들은 내용

AI로 코드를 짤 때 사람이 아직 검증해야 한다는 문제에서 출발했다. GitHub 저장소가 잘 된다고 주장해도 실제로 돌려 보면 아닌 경우가 많았다고 한다. AI로 철저히 검증하는 도구는 많이 나왔는데, 이 팀은 **저장소가 스스로 주장하는 내용이 실제로 되는지**를 검증하는 쪽을 만들었다.

에이전트 네 종류가 브라우저를 매번 돌려서 실제로 작동하는지 확인한다. 저장소의 Python 코드를 실제로 실행해 보기도 한다.

배포한 서비스를 시연했다. GitHub 저장소 주소만 넣으면 아래에 검증 결과가 바로 나온다. 사람의 피로도를 줄여 준다는 것이 요지였다.

### 분석 (추정)

**심사위원 자신이 사용자다.** 개발자와 빌더가 모인 자리에서 "README는 그럴듯한데 막상 안 돌아간다"는 경험은 거의 전원이 겪었다. 1팀의 체험단과 마찬가지로 문제 설명에 시간이 들지 않는다. 우리가 제약 규제를 먼저 설명해야 했던 것과 정반대다.

**검증을 주장이 아니라 실행으로 한다.** 코드를 읽고 판정하는 게 아니라 실제로 돌려 본다. 이 구조는 결과에 반박할 여지가 없다. 우리도 같은 원칙(`demo-verifier`가 직접 실행해 판정)을 썼지만 **내부 규율로만 두었고 제품으로 만들지 않았다.** 그쪽은 그 원칙 자체를 제품으로 세웠다.

**입력이 하나다.** 저장소 주소 한 줄이면 끝난다. 사용자가 설정할 것도, 이해할 것도 없다. 시연에서 주소를 붙여넣고 결과가 뜨는 장면만으로 설명이 끝난다.

**배포된 것을 보여줬다.** 로컬 터미널이 아니라 실제 서비스다. "이거 진짜 되나"라는 의심이 시연 중에 해소된다. 우리는 터미널 출력을 캡처해 슬라이드에 넣었는데, 배포된 화면을 보여주는 쪽이 같은 사실을 훨씬 적은 설명으로 전달한다.

**에이전트를 여러 개 쓴 이유가 자명하다.** 브라우저로 확인하는 것과 파이썬을 실행해 보는 것은 성격이 다른 작업이라, 나눈 이유를 설명할 필요가 없다. 우리가 네 플랫폼에 역할을 나눈 것도 같은 구조였지만, 그 필연성을 이해시키려면 규제 맥락을 먼저 깔아야 했다.

### 우리와의 대비

| | Does it actually run? | PharmaSignal |
|---|---|---|
| 심사위원과 사용자의 거리 | 심사위원 본인이 사용자 | 제약사 안전성 담당 |
| 입력 | 저장소 주소 한 줄 | 계열 이름(무엇을 넣을지 알아야 함) |
| 시연 형태 | 배포된 서비스 | 터미널 출력 캡처 |
| "실행으로 검증" 원칙 | 제품의 핵심 | 내부 개발 규율 |

## 3팀 · Job2Test

### 들은 내용

취업 인터뷰를 준비할 때 쓰던 백준 사이트가 문을 닫아 활용하지 못하게 되자 직접 만들었다고 한다. 코딩 테스트 준비를 염두에 둔 것으로 보인다.

채용 공고 링크에서 내용을 스크랩하고, Qwen으로 그 공고에 맞는 문제와 답을 만든다. 만든 문제가 실제로 맞는지 검증하는 단계도 있었다(어떤 플랫폼을 썼는지는 확인하지 못함).

특정 회사 공고를 넣으면 그 회사가 어떤 특성을 가졌는지 짚어 주고, 예상 테스트 문제를 낸 뒤 맞고 틀린 것을 채점해 준다. 취업에 도움이 되는 제품을 만들었다는 것이 요지였다.

### 분석 (추정)

**문제의 출발이 구체적인 사건이다.** "백준이 문을 닫아서 못 쓰게 됐다"는 날짜가 있는 사건이라 반박할 수 없다. 1팀의 "귀찮아서"와 같은 계열인데 더 강하다. 불편이 아니라 **쓰던 것이 사라진 상황**이기 때문이다. 우리가 든 근거는 "제약사 담당자가 매일 손으로 훑는다"였는데, 이건 사실이어도 심사위원이 목격한 적 없는 장면이다.

**공고를 문제로 바꾼다는 발상이 명확하다.** 채용 공고와 코딩 테스트는 원래 따로 노는 것인데 그 사이를 이었다. 무엇을 넣으면 무엇이 나오는지가 제목만으로 전달된다(Job to Test).

**결과가 점수로 나온다.** 맞고 틀린 것을 채점해 주므로 사용자가 해석할 일이 없다. 1팀이 복사해 쓰는 문구를 준 것과 같은 성격이다. **Top 3가 모두 사용자가 곧바로 쓰거나 확인할 수 있는 형태로 출력을 냈다.** 우리 출력은 집계 표였다.

**생성한 것을 검증하는 단계를 넣었다.** LLM이 만든 문제가 실제로 성립하는지 확인하는 구조인데, 2팀의 "주장이 아니라 실행으로 검증한다"와 같은 원칙이다. **상위 팀들이 생성물의 신뢰성을 다루는 방식을 공통으로 고민했다.**

**타깃이 넓고 절박하다.** 취업 준비생은 수가 많고 동기가 강하다. 심사위원이 본인이 아니어도 주변에 반드시 있어서 사용자를 상상하기 쉽다.

### 우리와의 대비

| | Job2Test | PharmaSignal |
|---|---|---|
| 문제의 출발 | 쓰던 서비스가 사라진 사건 | 실무에서 관찰한 비효율 |
| 제목의 설명력 | 이름만으로 입출력이 보임 | 이름으로는 무엇인지 알 수 없음 |
| 출력 | 채점 결과 | 집계 표 |
| 사용자 규모와 절박함 | 취업 준비생, 넓고 절박 | 제약사 안전성 담당, 좁음 |

## 4팀 · Exam Coach

**제목:** 틀린 번호가 아니라, 흔들린 개념을 찾습니다
**데모:** https://exam-coach-demo.geilesgruen.workers.dev/ (2026-08-22 기준 401로 열리지 않아 직접 확인하지 못했다. 아래는 발표에서 들은 내용 기준.)

### 들은 내용

전직을 준비하며 자격증을 여러 개 공부하다가 만들었다고 한다.

첫 화면에 "틀린 번호가 아니라, 흔들린 개념을 찾습니다"를 띄웠다. 틀린 문제를 통해 개념을 공부할 수 있게 하는 것이 핵심이다.

학습자용으로는 오늘 공부해야 할 범위를 한눈에 보여주고, 풀었던 문제 기록을 분석해 가장 복습이 필요한 개념을 짚어 주는 페이지가 있다. 틀린 것을 분석해 왜 틀렸는지 진단하고 어디부터 볼지 알려 준다.

강의자용도 있다. **학습자의 오답 분석이 강의자에게는 강의 보강 우선순위로 들어간다.** 강의 인사이트 페이지에서 확인한다.

플랫폼은 넷을 다 썼다. 보험 관련 자료를 대법원에서 공개된 것으로 **Bright Data**로 가져왔고, 2천 개가 넘는 문항의 정확성 검증에 **Daytona**를 썼고, 문항 일괄 태깅용 GPU로 **Nosana**를 연결했다.

QR 코드로 공개된 웹사이트 주소를 알려주고 데모 앱 화면도 보여줬다. 발표 시간은 넘겼다.

### 분석 (추정)

**우리와 구조가 가장 비슷한 팀이다.** 네 플랫폼에 역할을 나눴고, 공개 데이터를 수집해 LLM으로 구조화하고, 대량 처리를 외부 컴퓨트에 맡겼다. 그런데 결과가 갈렸다. 무엇이 달랐는지가 우리에게 가장 쓸모 있는 비교다.

**제목 한 줄이 통찰과 효용을 동시에 전달한다.** "틀린 번호가 아니라, 흔들린 개념을 찾습니다"는 기존 방식의 한계와 이 도구가 주는 것을 한 문장에 담았다. 듣는 순간 "맞다, 오답노트는 번호만 적었지"가 떠오른다. 우리 제목 PharmaSignal은 이름일 뿐 아무것도 설명하지 않았다.

**도메인이 특수한데 경험은 보편적이다.** 보험 자격증은 아는 사람이 적지만 **시험 보다가 틀려 본 경험은 전원이 있다.** 특수한 데이터를 쓰면서도 진입 장벽을 만들지 않는 방법이 여기 있다. 우리는 제약 규제라는 특수한 맥락을 특수한 채로 제시했다.

**같은 데이터로 두 사용자를 먹인다.** 학습자의 오답이 강의자에게는 보강 우선순위가 된다. 하나의 분석이 두 방향으로 쓰이는 구조는 제품 사고가 들어갔다는 신호다. 우리는 안전성 담당 한 사람만 봤다.

**Daytona를 규모로 썼다.** 2천 개가 넘는 문항의 정확성을 검증했다. 우리는 분석 스크립트 하나를 실행했다. 같은 플랫폼인데 **"쓸 수 있다"와 "이만큼 처리했다"는 다르게 읽힌다.**

**배포하고 QR로 열어 줬다.** 심사위원이 그 자리에서 자기 폰으로 들어가 볼 수 있다. 2팀의 배포 시연과 같은 성격인데 QR은 한 걸음 더 나간다. 우리는 터미널 캡처를 슬라이드에 넣었다.

**시간을 넘기고도 통과했다.** 시간 관리보다 내용과 실체가 앞선다는 뜻으로 읽힌다. 발표 시간에 맞추려고 내용을 깎을 이유는 없었다.

| 플랫폼 활용 | 4개 전부 | 3개 (Bright Data 미완) |
| 제목 | 통찰과 효용을 한 줄에 | 이름만, 설명 없음 |
| 도메인 특수성 | 데이터는 특수, 경험은 보편 | 데이터도 경험도 특수 |
| 사용자 | 학습자와 강의자 양쪽 | 안전성 담당 한쪽 |

| 접근 경로 | 배포 + QR로 즉시 체험 | 터미널 캡처 |

## 5팀 · Salesman

**구성:** Catch, Draft, Approve, Close — "4 layers, one pipeline"

### 들은 내용

영어로 발표해서 내용을 다 받아 적지는 못했다. 영업 업무에서 필요한 것을 만들었다고 한다.

파이프라인을 네 단계로 나눴고 각 단계 이름이 Catch, Draft, Approve, Close였다. "4 layers, one pipeline"이라는 표현을 쓰며 **네 플랫폼이 각각 어떻게 쓰였는지를 단계마다 짚었다.**

데모 페이지를 실제로 보여줬다. 페이지 안에서 네 플랫폼으로 아키텍처가 어떻게 구성됐는지 다시 보여주고, 파이프라인 흐름을 보여주고, 실행 화면까지 보여줬다.

### 분석 (추정)

**우리와 발상이 가장 가까운 팀이다.** 네 플랫폼을 하나의 파이프라인 단계에 대응시켰다는 점에서 PharmaSignal의 수집, 판단, 실행, 반출 금지와 같은 구조다. 그런데 전달 방식이 달랐다.

**단계 이름이 업무 동사다.** Catch, Draft, Approve, Close는 전부 영업 담당이 실제로 하는 행동이다. 플랫폼 이름이나 기술 계층이 아니라 **사용자의 일 순서**를 그대로 단계로 삼았다. 우리 단계 이름은 수집, 판단, 실행, 반출 금지였는데 앞의 셋은 기술 동작이고 넷째는 개념이다. 사용자가 하는 일이 아니다.

**"4 layers, one pipeline"이 심사 기준에 대한 직접적인 답이다.** 스폰서 활용도를 묻는 자리에서 네 개를 하나로 묶는 문구를 슬로건처럼 내놓았다. 심사위원이 채점표를 채우기 쉽게 만들어 준 셈이다. 우리도 같은 구조였지만 이렇게 한 문구로 압축해 반복하지는 않았다.

**아키텍처를 데모 페이지 안에서 보여줬다.** 슬라이드의 그림과 별개로, 실제 서비스 화면에서 구성과 흐름과 실행을 이어서 보여줬다. 설명과 실물이 같은 화면에 있으면 "설명은 그럴듯한데 진짜 되나"라는 간극이 생기지 않는다. 우리는 슬라이드의 SVG 도식과 터미널 캡처가 따로 있었다.

**Close까지 갔다.** 잡고, 초안 쓰고, 승인받고, 닫는다. 업무가 끝나는 지점까지 범위를 잡았다. 1팀이 신청글에서 블로그 글까지 간 것과 같은 성격이다. **상위 팀들은 공통으로 "그래서 일이 끝나는가"에 답했다.**

### 우리와의 대비

| | Salesman | PharmaSignal |
|---|---|---|
| 단계 이름 | 사용자의 업무 동사 | 기술 동작과 개념 |
| 플랫폼 묶음 문구 | "4 layers, one pipeline" 반복 | 문장으로만 설명 |
| 아키텍처 제시 | 데모 페이지 안에서 실물과 함께 | 슬라이드 도식과 캡처 따로 |
| 범위의 끝 | 거래 종결(Close) | 신호 정리, 판단은 사람 |

## 6팀 · OuroPlan

### 들은 내용

해커톤에서 아이디어는 있는데 비개발자라 무엇부터 해야 할지 모르는 상황에서 출발했다.

행사 링크를 올리면 그 행사에서 빠지면 안 되는 것을 **Bright Data**로 가져와 조건을 역산한다. GPU로 시뮬레이션을 돌려 **소요 시간과 성공률을 역산**한다.

발표에서 자기 프로젝트의 성공률이 40%로 나왔는데 실제로 그 안에 잘 들었다고 했다. 실제로 쓸 수 있도록 더 발전시킬 예정이라고 밝혔다.

### 분석 (추정)

**그 자리에 있는 모두의 문제를 골랐다.** 해커톤 참가자가 심사받는 자리에서 해커톤 참가자의 문제를 다뤘다. 심사위원도 주최자도 참가자도 전부 사용자다. **1팀부터 이어진 "심사위원이 곧 사용자" 패턴의 가장 극단적인 형태다.**

**자기 자신에게 도구를 적용해 결과를 보였다.** 성공률 40%가 나왔고 실제로 그 안에 들었다는 것은, 도구가 예측한 것을 발표 현장이 그대로 검증해 준 셈이다. **데모가 아니라 실증이다.** 우리는 파이프라인이 도는 것을 보여줬지만, 그 결과가 맞았는지를 증명할 방법은 없었다.

**미완성을 정직하게 말했다.** "실제로 쓸 수 있게 더 발전시킬 예정"이라고 했다. 완성도가 낮아도 통과했다는 뜻인데, 이는 심사가 완성도만 보지 않았다는 신호다. 우리는 게이트 4/4와 테스트 14개를 갖췄지만 그게 선정으로 이어지지 않았다.

**개념이 다소 추상적이다.** 조건 역산과 시뮬레이션은 무엇을 어떻게 계산했는지 설명이 필요한 영역이다. 그럼에도 통과한 이유는 문제 자체가 그 자리에서 즉시 이해됐기 때문으로 보인다. **문제의 접근성이 해법의 추상성을 덮었다.**

### 우리와의 대비

| | OuroPlan | PharmaSignal |
|---|---|---|
| 사용자와 심사위원의 거리 | 완전히 겹침 | 멀리 떨어짐 |
| 결과의 검증 | 발표 현장이 예측을 검증 | 검증할 방법 없음 |
| 완성도 | 미완성이라 밝힘 | 게이트 4/4, 테스트 14개 |
| 통과 요인(추정) | 문제의 접근성 | 해당 없음 |

이 팀이 우리에게 주는 가장 분명한 신호는, **완성도가 선정의 결정적 요인이 아니었다**는 점이다. 우리는 완성도에 시간을 크게 썼고 실제로 확보했지만, 그것이 문제의 접근성을 대신하지 못했다.
