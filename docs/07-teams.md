## 1팀 · ReviewForge

**발표자:** Minjoo Suh
**한 줄:** From local campaign application to verified review, one AI agent workflow.
**데모:** https://reviewforge-agentforge-seoul.vercel.app/
**테스트용 공고:** https://xn--939au0g4vj8sq.net/cp/?id=2270126
**발표 자료:** `presentation/ReviewForge_AgentForge_presentation.pdf` (6장)

> 발표 뒤 본인이 채팅방에 데모 링크와 자료를 공유하며 "발표에서 동기와 구현 기능을
> 충분히 설명하지 못한 것 같아 덧붙인다"고 밝혔다. 아래는 그 자료와 데모를 직접 확인한 내용.

### 들은 내용과 자료로 확인한 것

체험단 광고를 매번 읽고 파악해야 하는데 업체마다 조건이 달라 일일이 확인하는 것이 번거로웠다.
자료의 문구로는 **"I kept repeating the same work every time I applied."**

**흐름은 APPLY → VISIT → WRITE → VERIFY.** 공고 URL 하나를 붙여넣으면 제공 내역과 방문 조건,
후기 미션을 가져와 그 캠페인에 맞는 신청 문구를 만든다. 방문 뒤에는 사진과 실제 메모를 올리면
후기를 생성하고, 키워드 수와 글자 수, 미디어 개수 같은 캠페인 규칙을 검사한다.

데모에서 확인한 입출력은 이렇다. 입력은 **캠페인 URL과 본인 강점**(쉼표 구분, 500자 이내),
출력은 **신청 문구 3종**이다.

**네 플랫폼을 제품 단계에 하나씩 대응시켰다.** 자료 5장의 제목이
"Every sponsor tool is mapped to a real product step."

| 단계 | 플랫폼 | 하는 일 |
|---|---|---|
| 01 READ | Bright Data | 공개 공고 페이지에서 제공 내역, 방문 조건, 후기 미션 수집 |
| 02 SEE | Nosana | 업로드한 방문 사진을 GPU 추론으로 분석·분류 |
| 03 CREATE | Qwen Cloud | 캠페인 규칙 구조화, 신청 문구와 제목, 후기, 사진 순서 생성 |
| 04 VERIFY | Daytona | 키워드 수, 글자 길이, 미디어 개수, 필수 링크를 **고정 로직으로** 검사 |

두 경로가 나뉜다. 신청은 Bright Data → Qwen Cloud, 후기 작성은 Bright Data → Nosana →
Qwen Cloud → Daytona.

마지막 장의 요약은 **READ → UNDERSTAND → CREATE → VERIFY**이고,
"ReviewForge is not another AI writing tool."로 못 박았다.

### 분석

**심사위원에게 체험단을 먼저 설명했다.** 자료 2장이 "What is a blog experience campaign?"이다.
안다고 가정하지 않고 리뷰어가 얻는 것과 지역 상점이 얻는 것을 나눠 보여줬다. 처음에 나는 이 팀이
"설명이 필요 없는 주제를 골랐다"고 봤는데 **정확하지 않다. 설명이 필요한 것을 알고 한 장을 썼다.**
우리는 제약 규제를 설명 없이 전제로 깔았다. 차이는 주제의 난이도가 아니라 **설명을 준비했느냐**였다.

**아픈 지점은 문제 정의다.** 자료 3장 제목이 "The real pain is not just writing.
It is everything around it." 글쓰기만 자동화하는 도구는 이미 많으니, 그 앞뒤의 공고 읽기,
신청, 규칙 검사를 문제로 잡았다. 경쟁 도구와의 차이를 문제 정의 단계에서 미리 갈랐다.

**Daytona를 LLM이 아니라 고정 로직 실행에 썼다.** 키워드가 몇 번 나왔는지, 글자 수가 맞는지,
사진이 몇 장인지는 모델이 셀 일이 아니다. **생성은 Qwen이 하고 검사는 코드가 한다.**
우리가 내부 규율로 삼은 "만든 쪽과 검수하는 쪽을 나눈다"를 이 팀은 제품 안에 넣었다.
2팀의 "실행으로 검증한다"와 같은 계열이다.

**Nosana를 이미지에 썼다.** 업로드한 사진을 GPU로 분석·분류한다. GPU가 필요한 이유가
설명 없이 성립한다. 우리는 텍스트 추론에 1.5B 모델을 썼는데, 그건 "왜 GPU가 필요한가"를
규제 맥락으로 설명해야 했다.

**범위를 스스로 잘랐다.** "Focused on local, in-person experiences — product-shipping
campaigns are outside this MVP." 배송형 체험단을 뺀다고 명시했다. 못 한 것이 아니라
안 한 것이라고 밝히면 완성도가 오히려 올라간다.

**초기 분석의 오류 정정.** 나는 처음에 "플랫폼 하나를 깊게 썼다"고 적었으나 사실이 아니다.
**네 개를 다 썼고, 각각을 제품 단계에 대응시켜 슬라이드 한 장으로 보여줬다.**
구조는 우리와 같았다. 갈린 것은 단계 이름이 사용자의 행동(READ, SEE, CREATE, VERIFY)이었고
우리는 기술 동작(수집, 판단, 실행)과 개념(반출 금지)이었다는 점이다.

### 우리와의 대비

| | ReviewForge | PharmaSignal |
|---|---|---|
| 낯선 개념 | 한 장을 써서 설명 | 설명 없이 전제 |
| 문제 정의 | 글쓰기가 아니라 그 주변 | 흩어진 출처 수집 |
| 단계 이름 | READ, SEE, CREATE, VERIFY | 수집, 판단, 실행, 반출 금지 |
| Daytona 용도 | 규칙 검사(고정 로직) | 생성 코드 실행 |
| Nosana 용도 | 사진 분석·분류 | 텍스트 추론 |
| 범위 | 스스로 잘라내고 명시 | 잘라낸 것을 명시하지 않음 |
| 배포 | Vercel에 공개 | 로컬 CLI |

## 2팀 · Does it actually run?

**결과 페이지:** pineapplesour.github.io/does-it-actually-run/ (접속 가능)
**저장소:** github.com/pineapplesour/does-it-actually-run (공개)
**생성 05:30 UTC(14:30 KST), 최종 push 06:53 UTC(15:53 KST)**

### 확인한 내용

GitHub 저장소가 주장하는 대로 실제로 도는지 검증한다. 화면에 판정, 통과 샌드박스 3/3, 신뢰도 1.0이 카드로 떴다.

**설치 검증을 세 전략으로 나눠 돌린다.** README 문자 그대로(`literal-r1`, 3.5초), 누락 의존성 보충(`pragmatic-r1`, 10.3초), 최소 경로(`minimal-r1`, 6.9초). 셋 다 통과했고 화면에 이렇게 적혀 있었다.

> 승자는 모델이 고르지 않습니다. 실행 영수증으로 코드가 결정합니다.

**동작 검증은 네 루트다.** Playwright 로컬 크로미움과 **Bright Data Scraping Browser 원격 CDP**가 Verified, agent-browser와 dogfood는 `Not exercised`. 그리고 경고 박스에 **`completeFourRouteEvidence: false`** 와 함께 "안 돌린 루트를 통과로 세지 않습니다"라고 명시했다.

**가정을 측정으로 바꾼 대목이 핵심이다.** root 권한과 자유로운 네트워크를 가정했을 때 라운드1이 0/3 실패였는데, `uid=1001`, `sudo=passwordless`, `arbitrary_http_egress=blocked`로 실제 환경을 측정해 넘기니 3/3 통과였다. "Give the agent measured truth and it gets it right the first time."

**Nosana** 마켓 조회 로그도 보였다. 가용 GPU를 조회해 최저가 `nvidia-3060-community` $0.033/h를 골랐다.

### 분석

**"실행 영수증"이라는 표현이 이 팀의 전부를 요약한다.** 판정 주체를 모델에서 코드로 옮겼다는 선언이고, 그걸 화면의 숫자로 증명했다.

**안 돌린 것을 안 돌렸다고 화면에 썼다.** `Not exercised`와 `completeFourRouteEvidence: false`가 그대로 노출됐다. 우리도 같은 규율을 지켰다. **정직함은 우리와 이 팀의 공통점이지 차이가 아니었다.**

### 공개 저장소에서 확인한 것

발표 화면에는 Qwen Cloud가 안 보였지만 **저장소 README에는 네 플랫폼이 모두 표로 정리돼 있다.**
그리고 표에 **"필수성"** 열이 따로 있다.

| 스폰서 | 사용 제품 | 위치 | 필수성 |
|---|---|---|---|
| Bright Data | SERP API + **Scraping Browser (CDP)** | `src/brightdata.py` | 로컬 크롬은 GitHub에 막힌다. 원격 브라우저 N개 병렬이 곧 교차검증 |
| Qwen Cloud | Chat Completions (OpenAI 호환) | `src/qwen.py` | README 해석과 에러 되먹임 수정 |
| Daytona | Sandbox 생성 / exec / 삭제 | `src/daytona_runner.py` | **없으면 프로젝트가 성립하지 않는다.** 실제 실행이 유일한 진실 |
| Nosana | Markets / Jobs / API Keys | `src/nosana.py` | GPU 워커 선택 및 오프로드 |

README에 **"Bright Data는 제품 2종을 쓴다 (SERP + Browser API)"** 라고 따로 못 박아 두었다.

**설계 원칙 한 줄이 날카롭다.**

> 검증이 해결보다 싸고 게이트가 객관적인 곳에서만 분해한다.

그리고 판정 기준을 코드로 고정했다. `exit_code == 0 && stdout contains REPRO_OK` 이것만이 PASS이고,
신뢰도도 모델 자기신고가 아니라 실제 통과한 샌드박스 비율이다. "LLM 여러 개를 투표시키는 접근은
상관된 오류를 못 고친다"고 이유까지 적었다.

**저장소에 `video/demo.mp4`가 있다.** 화면 녹화 스크립트(`record.mjs`)까지 함께 두었다.
폴더 구조는 `deck/ docs/ evidence/ skills/ src/`로 우리와 거의 같다.

### 분석 보강

**우리가 못 한 것 두 가지를 이 팀은 했다.**

1. **데모 영상을 만들었다.** 우리는 정적 슬라이드만 냈다. 제출물 심사가 1차 관문이었으니
   이 차이가 컸을 수 있다.
2. **한 스폰서에서 제품을 두 개 썼다.** SERP API와 Scraping Browser를 둘 다 붙이고 README에
   명시했다. "More sponsor APIs integrated = higher score"라는 채점 방식에 정확히 대응한 셈이다.
   우리는 Bright Data 제품 하나(Web Unlocker)에 막혀 아예 0이 됐는데, **제품이 여러 개라는 것을
   알았다면 SERP API로 우회할 수 있었다.**

**필수성을 플랫폼마다 한 문장으로 적었다.** "없으면 프로젝트가 성립하지 않는다" 같은 문장은
평가자가 스폰서 통합 점수를 매길 때 그대로 근거가 된다. 우리도 같은 논리를 갖고 있었지만
발표 서사로만 풀었고 표로 만들지 않았다.

## 3팀 · Job2Test

**부제:** Company-specific mock coding tests from a job posting
**배포:** aiforge.jungwuk.com
**발표자:** Minseok Park, Jungwuk Yoo

### 확인한 내용

아키텍처 슬라이드의 부제 한 줄이 전부를 설명한다.

> **Bright Data reads, Qwen writes, Daytona proves**

파이프라인은 일곱 단계다. Read posting → Extract profile → Collect reviews → Summarize trends → Generate problem → Verify solution → Grade user code.

| 플랫폼 | 역할 | 하는 일 |
|---|---|---|
| Bright Data | **Eyes** | 공고, 면접 후기, 기술 블로그를 실시간 수집 |
| Qwen | **Brain** | 프로필, 트렌드 요약, 5개 테스트가 붙은 문제, 힌트. JSON mode |
| Daytona | **Hands** | 격리 샌드박스에서 정답 검증과 사용자 코드 채점 |

데모는 토스 서버 개발자 공고로 돌렸다. 수집한 근거를 화면에 나열했다. 토스뱅크 서버 개발자 면접 후기, 토스페이먼츠 코딩테스트 후기, 토스 기술 블로그다. 슬라이드 제목이 **"Demo 1: Problems come from evidence, not guesses"** 였고 "Every search query and source is visible"이라고 덧붙였다.

생성된 문제는 **Latency Budget Window**로, 대기 중인 작업의 지연 위험 점수가 주어질 때 합이 limit 이하인 연속 k개 블록의 가장 이른 시작 위치를 구하는 문제다. 풀이 화면에서 스켈레톤 코드를 주고, 제출하면 5개 테스트가 각각 38~74ms로 채점돼 **5/5 Accepted**가 떴다. 힌트는 "롤링 합을 쓰면 각 값이 창에 한 번 들어오고 한 번 나간다. 왜 O(n)인지 설명해 보라"였다.

### 분석

**"reads, writes, proves"는 여섯 단어로 세 플랫폼의 역할을 못 박는다.** Eyes, Brain, Hands라는 신체 비유까지 붙어서 듣는 사람이 해석할 일이 없다. 우리가 "수집, 판단, 실행, 반출 금지"라고 쓴 자리다.

**출처를 화면에 다 보여줬다.** "문제가 추측이 아니라 근거에서 나온다"는 주장을 근거 목록으로 뒷받침했다. LLM 생성물의 신뢰성 문제를 정면으로 다룬 셈이다.

**Nosana를 쓰지 않았다.** 아키텍처 슬라이드에 세 개만 있다. 그런데도 Top 6에 들었다.

## 4팀 · Exam Coach

**도메인:** 손해사정사 1차
**데모:** exam-coach-demo.geilesgruen.workers.dev

### 확인한 내용

슬라이드마다 좌측에 카피, 우측에 제품 스크린샷을 붙이고 우상단에 페르소나를 고정했다. "이정은 · 전직 준비 · 다수 자격증 수험생".

**학습자 화면.** "오늘은 이 한 가지부터". 전 회차 기록에서 오늘 할 한 가지를 먼저 정한다. 화면에 "제48회 · 손해사정이론 · Q33 열거위험담보와 입증책임 / 담보방식·입증책임 혼동"이 뜨고, "왜 지금?"에 "저장된 풀이 2건 · 오답 1회", 그리고 에이전트가 정한 다음 행동으로 "정답 근거를 한 문장으로 회상 → 24시간 내 재풀이"가 붙었다.

**진단 화면.** "틀린 번호가 아니라, 왜 틀렸는지와 어디를 다시 볼지를 연결합니다." 실제 진단 문구는 이랬다.

> 열거위험담보까지는 맞게 분류했지만, 보험사고가 담보위험으로 발생했다는 사실의 입증 주체를 보험자로 바꿨습니다. 통합 교재 p.89의 근거를 한 문장으로 회상한 뒤 24시간 안에 같은 함정 문항을 다시 푸세요.

교재 쪽수까지 짚는다.

**강의자 화면.** "학습자의 오답분석은 강의자에겐 강의 보강 우선순위로". 1순위 항목이 "손해사정이론 · 재보험 · 초과손해액재보험특약 — 응답한 16명 중 11명이 틀렸고 오답률 69%. 보강 수요 60/100"이었고, 권장 수정이 "다음 강의 첫 5분에 비교 설명 보강"이었다. **강사가 바로 실행할 수 있는 최소 변경안**까지 준다.

**규모 수치.** 자동 테스트 45개 통과, 기출 1,200문항과 내용 키워드 71개, 개인 답안 480건과 12회독 기록, 강사 자료 20개 총 1,886쪽.

**플랫폼 매핑.**

| 플랫폼 | 용도 |
|---|---|
| Bright Data | 보험개발원 공개 게시판 갱신 감지 |
| Daytona | 1,200문항 정합성 격리 검증 |
| Nosana | 문항 일괄 태깅용 GPU 추론 |
| Qwen Cloud | 근거 제한 오답 진단 |

**한계를 여러 군데에 명시했다.** "정밀 진단은 대표 7문항(개념 6 + 계산 1) 수동 검수 범위", "화면의 수치는 시연용 합성 데이터(합성 학습자 50명 · 완료 풀이 150회)이며 실제 학습자 데이터가 아닙니다", "강의 ID·영상 구간 미연결", "학습성과 개선 미입증", 그리고 플랫폼 표 옆에 **"어댑터 사전검사 4/4 · 현장 실제 호출 0/4"**.

데모 화면에는 에이전트 실행 기록이 4단계로 남는다. 보험개발원 확정답안(정답 검증) → 강사 자료 페이지 색인(학습 근거 검색) → **Qwen Cloud · qwen-plus**(오답 진단) → Exam Coach 정책(다음 학습 결정).

### 분석

**우리에게 가장 중요한 발견이 여기 있다.** 이 팀은 플랫폼 표 옆에 **"현장 실제 호출 0/4"** 이라고 스스로 적었다. 그런데 2위를 했다.

우리는 세 플랫폼을 실제로 호출했고 그걸 요약표에 초록색으로 표시했으며, 못 붙인 하나를 폴백으로 명시했다. **실호출 숫자만 보면 우리가 3, 저쪽이 0이다.** 그런데 1차 관문에서 우리가 걸렸다.

차이는 **무엇을 화면의 중심에 놓았느냐**다. 저쪽은 네 플랫폼과 용도를 표로 앞세우고 실호출 여부를 주석으로 달았다. 우리는 4단계 요약표를 앞세웠는데 그 표의 한 줄이 "폴백"이었다. 같은 정직함인데 **채점되는 축 위에 결함을 올려놓았느냐**가 갈렸다.

이건 "숨겼어야 했다"는 뜻이 아니다. 정직함은 양쪽 다 지켰다. 다만 **주장은 매핑으로 하고 한계는 주석으로 다는 편이, 결함을 표의 한 줄로 만드는 것보다 전달에 유리하다.**

**규모를 숫자로 보여줬다.** 1,200문항, 480답안, 1,886쪽. 우리 수치는 임상시험 20~40건이었다.

**같은 데이터가 두 사용자를 먹인다.** 학습자의 오답이 강사의 보강 우선순위가 되고, 그게 B2B 사업 구조로 이어진다. "인강 플랫폼이 이미 보유한 강의·교재 위에 분석만 얹는 B2B 계층"이라고 명시했다.

**진단이 행동으로 끝난다.** "24시간 안에 같은 함정 문항을 다시 푸세요", "다음 강의 첫 5분에 비교 설명 보강". 우리 출력은 "후기비중 50%"였다.

## 5팀 · Salesman (Sales Bench)

**제목:** Never miss a customer while you work.
**부제:** Your AI response agent for phone · email · messages
**대상:** Solo founders & busy workers

### 확인한 내용

문제는 바빠서 놓치는 고객 문의다. 전화, 이메일, 메시지, 웹사이트 폼으로 들어온 문의를 놓친다. 놓친 문의를 한곳에 모아 자격 판정하고 답장을 자동 생성한다.

아키텍처 슬라이드 제목이 **Four layers. One pipeline.** 이고 표는 이렇다.

| Layer | What it does |
|---|---|
| Bright Data | Collect public pages, prices, and copy for outreach signals |
| QwenCloud | Korean outreach drafts and policy-aware reply generation |
| Nosana GPU | Intent scoring and batch inference (credits through 8/25) |
| Daytona | Isolated policy lint — discounts, bank accounts, banned claims |

### 분석

**1위 팀의 슬라이드가 가장 단순하다.** 제목 한 줄, 부제 한 줄, 그리고 4행짜리 표 하나. 해석할 것이 없다.

**"Never miss a customer while you work."** 문제와 효용이 한 문장에 있고 손해가 눈에 보인다. 놓친 문의는 곧 잃은 매출이다.

**Daytona를 정책 린트에 썼다.** 할인, 계좌번호, 금지 표현을 격리 환경에서 검사한다. **LLM이 쓴 답장을 코드가 검사하는 구조**로, 3팀의 "Daytona proves", 1팀의 규칙 검사와 같은 계열이다. **다섯 팀 중 셋이 Daytona를 생성물 검증에 썼다.** 우리는 생성 코드 실행에 썼다.

**Nosana를 의도 점수화와 배치 추론에 썼다.** 대량 분류라 GPU가 필요한 이유가 설명 없이 성립한다.

**Four layers, One pipeline이라는 제목 자체가 채점표다.** 스폰서 통합이 점수인 대회에서 네 개를 하나로 묶는 문구를 슬라이드 제목으로 올렸다.

## 6팀 · OuroPlan

### 확인한 내용

로컬 화면(`127.0.0.1:5173/?proof=1`)으로 시연했다. 헤더가 "OuroPlan 결정론적 태스크 토폴로지"이고 배지가 `CACHED REAL RECEIPTS`, 우측에 `16:19:12 KST`가 찍혀 있었다.

**입력이 이 해커톤 자체였다.**

- 행사 URL: `https://luma.com/agentforgeseoul`
- 프로젝트 목표: "15:30까지 실제 실행 증거가 있는 작동 데모 제출"
- 계획 기준 시각: 2026-08-22 14:55
- 마감 시각: 2026-08-22 15:30

**01 WITNESS — 단일 실패 확정.** 행사 안내문에서 마감이 15:30이라는 것, 코드 수준 통합이 필요한 스폰서 제품 네 개가 명시돼 있다는 것, 그리고 네 제품 중 어느 것에 대해서도 실행 로그나 응답 ID나 통합 증거가 입력에 없다는 것을 확정했다.

**02 PREIMAGE — 최소 선행조건 역산.** 35분 안에 완수할 파이프라인을 작업별 소요 시간과 함께 역산했다.

| 작업 | 소요 |
|---|---|
| Bright Data 웹 스크레이핑으로 데드라인·스폰서 요구사항 증거 수집 | 5분 |
| QwenCloud 추론 API로 실행 계보 역산 및 의존성 그래프 생성 | 5분 |
| Nosana GPU 노드에서 스트레스 테스트 실행 및 서명된 인증서 해시 확보 | 8분 |
| Daytona 워크스페이스에서 산출물 통합 실행 검증 및 로그 캡처 | 7분 |
| 최종 데모 패키지 번들링 및 제출 | 10분 |

### 분석

**입력이 그 방에 있는 모두의 오늘이었다.** 14:55에 시작해 15:30까지 무엇을 해야 하는지를 역산했는데, 그건 청중 전원이 몇 시간 전에 실제로 겪은 일이다. 데모를 이해하는 데 상상이 필요 없었다.

**이 팀이 역산한 계획이 곧 우리가 실패한 지점이다.** Nosana 8분, Daytona 7분, Bright Data 5분. 우리는 Bright Data에서 크레딧 신청과 zone 생성과 카드 요구에 막혀 결국 못 붙였다. **같은 문제를 우리는 겪었고 저 팀은 도구로 만들었다.**

**미완성이라 밝히고도 3위를 했다.** 완성도가 결정적 요인이 아니었다는 가장 분명한 증거다. 최종 3팀은 참가자 투표로 뽑혔고, 투표하는 사람은 방금 같은 고생을 한 참가자들이었다.

**"실패에서 거꾸로, 증거로 앞으로"라는 문구가 발상을 압축한다.** 성공 경로를 짜는 게 아니라 실패를 먼저 확정하고 그 역상을 구한다.

## 다섯 팀에서 반복된 것

여섯 팀의 슬라이드와 녹취를 다 보고 나서 반복 확인된 것들이다.

**1. 문제의 주인이 그 방에 있었다.** 체험단, 안 도는 저장소, 코딩테스트, 자격증, 놓친 고객 문의, 해커톤 계획. 전부 청중이 겪었거나 겪는 일이다. 우리 문제의 주인은 제약사 안전성 담당이었다.

**2. Bright Data를 쓴 팀이 다섯이다.** 문제 형태도 "공개 웹의 흩어진 정보를 모아 개인 작업을 대신한다"로 반복된다. **우리 파이프라인도 같은 형태였다.** 그러니 형태가 문제가 아니었다.

**3. Daytona를 생성물 검증에 쓴 팀이 셋이다.** 정답 검증(Job2Test), 정책 린트(Salesman), 규칙 검사(ReviewForge). LLM이 만든 것을 코드가 검사한다는 구조를 여러 팀이 독립적으로 도달했다. 우리는 생성 코드 실행에 썼다.

**4. 안 돌린 것을 밝힌 팀이 셋이다.** `completeFourRouteEvidence: false`(2팀), "현장 실제 호출 0/4"와 "시연용 합성 데이터"(4팀), "더 발전시킬 예정"(6팀). **정직함은 우리와 이들의 공통점이다.**

**5. 단계 이름이 사용자의 행동이었다.** READ·SEE·CREATE·VERIFY(1팀), Eyes·Brain·Hands(3팀), Catch·Draft·Approve·Close(5팀). 우리는 수집·판단·실행·반출 금지였다.

**6. 배포하고 주소를 줬다.** ReviewForge, Job2Test, Exam Coach는 접속 가능한 주소가 있었다. 우리는 로컬 CLI였다.

관점별로 한 팀씩만 선택하는 방식이었다. 세 관점을 서로 다른 팀에 나눠 주었다.

Real-life에서는 Job2Test(문제의 무게는 더 크나 빈도가 낮음).

### 내 판단이 어디서 어긋났나

**개념의 참신함을 과대평가했다.** "Does it actually run?"에 Innovation 만점을 준 것은
"저장소의 주장을 실행으로 검증한다"는 각도가 영리해 보였기 때문이다. 그런데 발표자 본인도
"AI로 철저히 검증하는 도구는 많이 나왔다"고 말했다. 이미 붐비는 영역이었고, 개발자 도구라
사용자층도 좁다. **영리함과 설득력은 다른 축인데 나는 둘을 섞어 봤다.**

**완성도를 과대평가했다.** OuroPlan에 완성도 2점을 주고 최하위에 뒀는데 3위에 들었다.
미완성이라고 스스로 밝혔는데도 그렇다. 성공률 40%가 나왔고 실제로 그 안에 들었다는
**한 장면이 기억에 남는 힘**을 나는 점수로 환산하지 못했다.

**플랫폼 매핑의 전달력을 과소평가했다.** Salesman의 "4 layers, one pipeline"은 슬로건이
아니라 채점을 쉽게 만드는 장치였다. Catch, Draft, Approve, Close라는 업무 동사 네 개에
플랫폼 네 개가 얹히면 듣는 사람이 따로 해석할 일이 없다. 나는 이걸 "익숙한 구성"으로
낮게 봤는데, 익숙한 것이 곧 전달이 잘 되는 것이었다.

**돈이 걸린 도메인의 무게를 놓쳤다.** 영업은 매출로 직결된다. 심사위원이 사업적 가치를
가늠할 때 가장 짧은 경로다.

### 이 오류가 우리 프로젝트의 실패와 같은 뿌리다

나는 PharmaSignal을 설계할 때 개념의 정교함(민감도에 따른 추론 경로 분리)과
완성도(게이트 4/4, 테스트 14개)에 무게를 실었다. 그리고 다른 팀을 평가할 때도
정확히 같은 기준으로 점수를 매겨 또 틀렸다.

**같은 편향이 두 번 작동했다.** 만들 때 한 번, 평가할 때 한 번. 이건 정보 부족이 아니라
판단 기준의 문제다. 다음에는 "이게 얼마나 영리한가" 대신 **"듣는 사람이 몇 초 만에
자기 일로 받아들이는가"**를 먼저 묻는다.
