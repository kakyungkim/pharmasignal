# 01. 실행 계획 (1시간)

> 선정 주제의 근거는 [00-topic-selection.md](00-topic-selection.md), 제품 명세는 [02-prd.md](02-prd.md) 참조.

## 승부 방식

시간이 1시간 남짓이라 완성도 높은 큰 제품은 불가능함. **얇지만 끝까지 도는 파이프라인 한 줄기 + 발표자료**로 간다. 스폰서 활용도 점수는 아키텍처 설계 자체에서 확보하고, 남는 시간을 실동작 증거와 스토리에 씀.

---

## 시간 배분

| 구간 | 할 일 | 산출 |
|---|---|---|
| T+0~5 | 미가입 2곳 가입·키 발급. **Nosana를 제일 먼저** 걸어 두고 대기 중 다른 작업 진행 | `.env` 4종 |
| T+5~20 | `python smoke_test.py` 로 플랫폼별 최소 1콜 독립 검증. 통합은 절대 먼저 하지 않음 | 성공 로그 4건 |
| T+20~40 | `python run_demo.py GLP-1` 완주. 성공한 플랫폼부터 실경로로 전환 | 데모 1회 완주 |
| T+40~52 | 슬라이드 6장 + 실행 화면 캡처 | 발표자료 |
| T+52~60 | 제출, 2분 리허설 | 제출 완료 |

## 규율 두 가지

1. **5분 룰** — 어떤 단계든 5분 넘게 막히면 즉시 폴백으로 전환하고 다음으로 감. 막힌 단계를 붙잡는 것이 이런 해커톤의 최대 실패 요인임.
2. **성공 즉시 캡처** — 단계가 통과하는 순간 터미널 스크린샷을 남김. 마지막에 통합이 어긋나도 "각 플랫폼을 실제로 호출했다"는 증거가 발표자료에 남는다.

---

## 키 발급 위치

| 플랫폼 | 어디서 | 환경변수 |
|---|---|---|
| Bright Data | 대시보드 > Web Unlocker zone > Overview 탭. 키는 생성 직후 한 번만 표시됨 | `BRIGHTDATA_API_KEY`, `BD_ZONE` |
| Qwen Cloud | 콘솔 API 키 발급 | `DASHSCOPE_API_KEY` |
| Daytona | 대시보드 > API Keys | `DAYTONA_API_KEY` |
| Nosana | 템플릿 배포 후 받은 추론 엔드포인트 URL | `NOSANA_BASE_URL`, `NOSANA_MODEL` |

---

## 폴백

코드에 이미 폴백이 내장되어 있어 키가 없어도 파이프라인은 끝까지 돈다(확인 완료). 발표에서 쓸 대응은 다음과 같음.

- **Nosana 배포 미완** → 배포 진행 화면을 캡처하고, 아키텍처상 그 자리가 하는 일을 설명. 나머지 3단계는 실동작으로 보여줌.
- **Bright Data zone 설정 문제** → ClinicalTrials.gov는 공개 REST API라 직접 호출로도 데이터가 나옴. Bright Data는 봇 차단이 있는 전문지 한 곳에만 걸어 성공 로그를 확보.
- **Daytona 지연** → 미리 한 번 돌려 캡처해 둔 화면을 씀.
- **전부 어긋남** → 4단계 아키텍처 그림 + 스모크 테스트 성공 로그 4장이면 스폰서 활용도는 지켜짐.

---

## 슬라이드 6장

한 장에 한 메시지, 항목은 명사형 종결.

1. **문제** — 신약 안전성 신호가 공시, 문헌, 뉴스에 흩어져 사람이 매일 훑는 현실
2. **해법** — PharmaSignal, 수집부터 근거 차트까지 잇는 에이전트
3. **아키텍처** — 4단계 그림, 각 칸에 스폰서 로고
4. **데모** — 실행 화면 캡처 3장
5. **왜 4개가 다 필요한가** — 규제 때문에 Nosana 경로가 필요한 이유
6. **다음 단계** — 매일 돌아가는 감시, 사내 배포 형태

---

## 검증

- 스모크 테스트 4건이 각각 실제 응답을 출력하는지 터미널에서 확인하고 캡처.
- `run_demo.py`를 처음부터 끝까지 완주시키고 단계별 출력이 비어 있지 않은지 확인.
- 발표 전 2분 리허설 1회. 라이브 실행과 캡처 화면 두 벌을 준비해 현장 와이파이가 느려도 진행되게 함.
