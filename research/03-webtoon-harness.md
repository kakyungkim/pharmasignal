# 03. webtoon-harness 조사: 웹툰 자동 제작 하네스에서 가져올 것

> 작성 2026-08-23 · 대상: [revfactory/webtoon-harness](https://github.com/revfactory/webtoon-harness) (MIT, 공개 저장소)
> 목적: PharmaSignal 소개 카드뉴스형 웹툰을 다시 만들기 전에, 이 하네스의 설계에서 배울 것과 우리 환경에서 바로 쓸 수 있는 것을 가린다.
> 저장소는 `git clone --depth 1`로 전문을 내려받아 27개 에이전트 정의와 6개 스킬 문서를 모두 읽었다. **이미지 생성 경로는 이 세션에서 직접 실행해 결과 이미지를 눈으로 확인했다**(§3-2, §4-2). 실행하지 않은 것은 그렇게 적었다.

## 요약

| 질문 | 답 |
|---|---|

| 이미지 생성 | **codex CLI의 `image_generation` 도구.** OpenAI API 키가 아니라 ChatGPT 로그인(OAuth)으로 쓴다. 별도 유료 이미지 API 키가 필요 없다 |

| 캐릭터 일관성 | 하네스는 (1) 레퍼런스 시트 선행 렌더, (2) 불변 외형 토큰 전 프롬프트 주입, (3) 검증-재생성 루프의 세 겹으로 잡는다. **다만 레퍼런스 PNG를 프롬프트에 실제로 첨부하지는 않는다.** 우리는 이 빈틈을 메울 수 있다(§4-2) |
| 한글 말풍선 | 별도 레이어가 아니라 **이미지 생성 시 작화에 함께 그린다**(in-image 베이크). 실측 결과 짧은 한글은 두 번 다 정확히 나왔다 |
| 가져올 자산 | 세로 스크롤 뷰어 HTML 템플릿, 연출 어휘 카탈로그, QA 검증 명령 모음, 일관성 토큰 작성법, 6축 검증 기준 |

## 1. 무엇을 하는 하네스인가

### 1-1. 입력과 출력

입력은 자연어 한 줄이다. "트렌드 반영해서 웹툰 1화 만들어줘" 정도면 된다. 장르 방향, 수위, 길이 같은 제약을 덧붙일 수 있다.

출력은 `_workspace/RELEASE/ep{NN}/` 아래에 다음이 놓인다.

- `index.html`: 세로 스크롤 웹툰 뷰어(외부 의존성 없는 단일 HTML)
- `panels/`: 패널 PNG 50장 이상. 말풍선과 한글 대사가 이미 그림 안에 들어 있다
- `qa_report.md`: 품질 합격 근거
- `RELEASE_NOTES.md`: 사인오프 판정, 포함 목록, 다음 회차 시드

중간 산출물도 전부 남는다. 트렌드 브리프, 세계관, 캐릭터, 시리즈 아크, 반전 계획, 긴장 곡선, 비트시트, 대본, 스타일 바이블, 캐릭터 시트, 레퍼런스 시트, 샷리스트, 레터링 명세, 프롬프트 목록, 검증 보고서까지 15종 남짓이 단계별 디렉터리에 쌓인다. 저장소는 이것을 감사 추적이라 부른다.

### 1-2. 저장소에 실제로 들어 있는 것

이 점을 먼저 분명히 해야 한다. **실행 코드가 없다.** 저장소 전체가 다음으로 구성된다.

```
.claude/agents/     27개 .md   (에이전트 프롬프트 정의)
.claude/skills/      6개 SKILL.md + references 4개 + assets 1개
docs/images/         5장       (README용 인포그래픽)
README.md, LICENSE, .gitignore
```

파이썬 스크립트도, 셸 스크립트도 없다. 3,062줄의 마크다운이 전부다. 실행은 Claude Code가 이 정의를 읽어 에이전트를 띄우고 codex CLI를 호출하는 방식으로 이뤄진다. `_workspace/`, `RELEASE/`, `**/*.png`가 모두 `.gitignore`에 걸려 있어 예제 결과물도 없다.

한 가지 빠진 의존성이 있다. 배치 렌더 헬퍼로 `~/.claude/skills/codex-image/scripts/codex_imagegen_batch.sh`를 부르는데, 이 스킬은 저장소에 포함되지 않고 [revfactory/skills의 codex-cli 스킬](https://github.com/revfactory/skills/tree/main/codex-cli)로 링크만 걸려 있다. 우리 로컬에도 `~/.claude/skills/codex-image`는 없다. 배치 병렬이 필요하면 우리가 직접 짜야 한다.

저장소 상태(2026-08-23 확인): 스타 305, 포크 108, MIT 라이선스, 마지막 푸시 2026-06-28.

## 2. 파이프라인 구조

### 2-1. 4팀 6단계

| 단계 | 팀 | 인원 | 하는 일 | 핵심 산출물 |
|---|---|---|---|---|
| Phase 0 | 없음 | — | 컨텍스트 판별(신규/다음 화/부분 재실행/새 기획) | — |
| Phase 1 | 없음 | — | 회차 번호·제약 기록, 작업 디렉터리 생성 | `00_input/brief.md` |
| Phase 2 | 리서치 | 5 | 장르 동향, 플랫폼 랭킹, 독자 반응, 후킹·반전 역설계 → 종합 | `trend-brief.md` |
| Phase 3 | 시나리오 | 9 | 하이콘셉트 → 세계관 → 캐릭터 → 시리즈 아크 → 반전·긴장 곡선 → 비트시트 → 대본 → 교정 | `ep{NN}_script_final.md` |
| Phase 4 | 비주얼 | 9 | 스타일 바이블 → **레퍼런스 시트 선행 렌더** → 샷리스트·레터링 → 프롬프트 합성 → 패널 렌더 → 6축 검증 루프 | `panel_*.png`, `validation.md` |
| Phase 5 | 조립검수 | 4 | 세로 스크롤 조립 → QA → 연속성 갱신 → 사인오프 | `index.html`, `qa_report.md` |
| Phase 6 | 없음 | — | 결과 요약, 피드백 수집 | — |

세션당 활성 팀이 하나뿐이라는 제약 때문에, 단계마다 `TeamCreate`로 팀을 만들고 끝나면 `TeamDelete`로 지운다. 팀 사이의 인수인계는 메모리가 아니라 `_workspace/`의 파일로 한다. 컨텍스트를 아끼는 구조이면서, 동시에 어느 단계든 따로 다시 돌릴 수 있게 만드는 장치이기도 하다.

### 2-2. 배울 점 세 가지

**하나. 단계를 나눈 기준이 "산출물의 종류"다.** 대본, 스타일, 콘티, 레터링, 프롬프트, 픽셀, 조립이 각각 다른 파일로 분리된다. 그래서 "반전 더 강하게"는 시나리오팀만, "패널 23번 다시 그려"는 비주얼팀 일부만 다시 돌리면 된다. 우리 6컷도 대본과 조판이 한 파이썬 파일에 붙어 있어서 "그림만 다시"가 불가능했다.

**둘. 그리기 전에 규격을 문서로 확정한다.** 스타일 바이블 8섹션(작화 스타일, 팔레트, 톤, 화면비, 일관성 규약, 장소 토큰, 말풍선 규약, 금지사항)을 먼저 쓰고, 캐릭터 시트로 외형을 토큰화하고, 그 다음에야 첫 픽셀이 나온다. 우리는 이 단계 없이 바로 SVG를 그렸다.

**셋. 재작업에 상한을 둔다.** 패널당 재생성 최대 3회, 단계별 재작업 루프 최대 2회. 초과하면 `ACCEPT-FLAG`(통과시키되 한계를 보고서에 명시)로 마감한다. 완벽을 못 이룰 때 무한 루프에 빠지지 않고 한계를 기록하고 넘어가는 규율이다.

## 3. 이미지 생성 경로

### 3-1. 하네스가 쓰는 것

`codex exec`의 `image_generation` 도구 하나다. 호출은 이렇게 생겼다.

```bash
codex exec --sandbox workspace-write --skip-git-repo-check \
  --cd <작업디렉터리> -o /tmp/codex-ep01-001.md \
  "이미지 생성 도구로 '<프롬프트>' 이미지를 생성하고 ./panel_001.png 로 저장. 파일 경로만 한 줄로 보고."
```

인증은 **ChatGPT OAuth**다. OpenAI API 키를 따로 사지 않는다. 대신 ChatGPT 플랜의 메시지 한도를 소모하며, 저장소도 "헤비 배치(50장+) 전 플랜 잔량을 확인하라"고 적어 두었다.

동시성 규약이 이 하네스에서 가장 구체적인 부분이다. codex 전역 동시 세션은 5개를 절대 넘기지 않는다. 아티스트 에이전트가 3명이어도 `codex exec` 동시 실행 총합이 5 이하가 되도록 오케스트레이터가 순차 디스패치한다. 저장소가 밝힌 실측치는 5장 동시 렌더에 wall-clock 약 158초, 50장이면 10웨이브에 26~28분이다.

### 3-2. 우리 환경 실측 (2026-08-23 직접 실행)

```
codex --version        → codex-cli 0.147.0
codex login status     → Logged in using ChatGPT
codex features list    → image_generation   stable   true
```

세 줄 모두 통과했다. 실제로 웹툰 패널을 생성해 봤고, 결과는 `webtoon/_codex_test/panel_test.png`에 있다.

- 크기 1122 x 1402 (4:5 세로), 약 1.9MB PNG
- 화풍: 셀 셰이딩 한국 웹툰 화풍. 우리가 SVG로 그린 납작한 아이콘형 인물과는 종류가 다른 결과물이다
- 말풍선 안 한글 "신호가 또 늘었어요"가 **오탈자 없이 정확히** 렌더됐다
- 생성된 PNG는 `~/.codex/generated_images/` 아래에 먼저 떨어지고, 프롬프트에 "./경로로 저장"을 지시하면 codex가 작업 디렉터리로 복사한다

즉 **유료 이미지 API 키 없이 지금 바로 웹툰 화풍 패널을 만들 수 있다.** 이것이 이번 조사에서 가장 중요한 발견이다.

한 가지 단서를 붙인다. 무료 ChatGPT 계정에서도 `image_generation`이 열리는지는 확인하지 못했다. 이 환경은 이미 로그인된 상태였고, 어떤 플랜인지는 조회하지 않았다. [Gap:Assumption]

## 4. 캐릭터 일관성을 어떻게 유지하는가

### 4-1. 하네스의 3중 장치

**(1) 레퍼런스 시트 선행 렌더.** 패널을 그리기 전에 주요 캐릭터마다 두 장을 먼저 만든다. `{IDTAG}_turnaround.png`(정면·3/4·측면·후면 전신, 무채색 배경, 균일 조명, 무표정)와 `{IDTAG}_expressions.png`(핵심 표정 3~4종 클로즈업)다. 레퍼런스만은 텍스트 없이 렌더한다. 깨끗한 외형 도감이어야 기준 노릇을 하기 때문이다. 이 파일들은 회차 폴더가 아니라 시리즈 자산으로 `04_visual/refs/`에 두고 다음 회차에 재사용한다.

**(2) 불변 토큰과 가변 토큰의 분리.** 외형에서 절대 안 바뀌는 것(머리색·길이, 눈 모양, 체형, 식별 표식)을 불변 토큰으로 묶고, 표정·포즈·의상·조명은 가변으로 뺀다. 불변 토큰은 등장하는 모든 패널 프롬프트에 글자 그대로 주입된다.

```
## 지호 (주인공)
- identity_tag: JIHO
- 고정 외형 토큰:
  "20s Korean man, short tousled black hair, sharp single-lid eyes,
   slim build, faint scar on left brow, charcoal hooded jacket"
- 금지: 머리색·눈매·흉터 변경 금지
```

작성 요령이 구체적이다. 문장이 아니라 고밀도 명사구로 쓰고, 흉터·점·안경·머리핀 같은 **식별 표식을 1~2개 박고**, 한 패널에 여러 인물이 나오면 각자의 표식이 구분되게 배치한다. 영문 키워드를 쓰되 한국인 외형은 "Korean"을 명시한다.

**(3) 배경에도 같은 장치.** 캐릭터처럼 배경도 흔들린다는 관찰에서 나온 `LOC_*` 장소 토큰이다. 장소마다 고정 배경 키워드 세트를 정의하고, 같은 `scene_id`의 모든 패널에 같은 토큰을 주입한다. 장소 전환은 명시적 `SCENE BREAK`에서만 일어난다. 저장소는 EP01에서 같은 장면인데 도로가 갑자기 실내로 바뀌는 사고가 실제로 났다고 적고 있다.

### 4-2. 하네스가 놓친 것, 우리가 쓸 수 있는 것

여기서 중요한 발견이 하나 더 있다. **하네스는 레퍼런스 PNG를 프롬프트에 실제로 첨부하지 않는다.** prompt-smith 정의를 보면 "레퍼런스 앵커"란 이런 문구를 프롬프트 텍스트에 넣는 것을 뜻한다.

> "match the exact appearance of {IDTAG} as defined in the locked character reference sheet: <불변 토큰>"

파일 경로를 말로 언급할 뿐, 이미지 자체는 모델에 들어가지 않는다. 결국 텍스트 토큰만으로 일관성을 노리게 되고, 그래서 6축 검증 루프로 이탈을 잡아내는 사후 장치가 따로 필요해진다.

그런데 codex CLI에는 입력 이미지를 붙이는 플래그가 있다.

```bash
codex exec -i <참조이미지.png> -- "<프롬프트>"
```

이것을 실제로 시험했다. 앞서 만든 패널을 참조로 붙이고 "완전히 같은 인물이 등장하는 새 패널"을 요청한 결과가 `webtoon/_codex_test/panel_test2.png`다.

**결과: 얼굴, 단발 검은머리, 둥근 안경, 남색 재킷이 그대로 유지됐다.** 장면(책상 앞 → 회의실 화이트보드), 포즈, 조명, 표정은 요청대로 바뀌었고 인물 동일성은 눈으로 보아 확실하다. 말풍선의 한글 "이건 사람이 놓친 신호예요"도 정확했다.

컷이 6~8장 규모인 카드뉴스에서는 이 방식이 하네스의 텍스트 토큰 방식보다 낫다. 첫 컷을 캐릭터 기준으로 확정한 뒤, 나머지 컷을 전부 `-i 기준컷.png`로 파생시키면 된다. 인자 순서에 주의할 점이 하나 있다. `-i`가 가변 인자라 파일 뒤에 프롬프트를 바로 두면 프롬프트까지 삼킨다. `--`로 끊거나 프롬프트를 앞에 둬야 한다.

## 5. 한글 텍스트 처리

### 5-1. 이 하네스의 선택: in-image 베이크

말풍선과 한글 대사를 **이미지 생성 시 작화에 함께 그린다.** HTML 오버레이도, 포토샵 타이핑도, 어떤 후작업 합성도 금지한다고 여러 문서에서 반복해 못 박는다. 그래서 부정 프롬프트에 `no text`를 쓰지 않고 `no watermark, no English text, no gibberish/garbled/misspelled text`만 쓴다.

이유는 저장소에 적힌 EP01 피드백에서 나온다. 텍스트를 나중에 얹으면 독자가 "후작업으로 붙였다"고 알아보고, 그 순간 웹툰이 슬라이드처럼 읽힌다. 그래서 검증 기준 C3에 (d)항이 따로 붙어 있다.

> 말풍선·텍스트가 작화에 녹아든 손그림 잉크 톤인가. 깨끗한 디지털 고딕 폰트를 평평하게 위에 얹은 "오버레이/붙여넣기" 느낌이면 **글자가 맞아도 REGEN**.

오버레이-룩 판별 신호까지 열거해 두었다. 획 두께가 기계적으로 균일한가, 자간·행간이 자로 잰 듯 완벽한가, 시스템 고딕 룩인가, 글자 가장자리가 작화보다 과하게 매끈한가, 검정 톤이 그림과 분리돼 보이는가. 그리고 텍스트 보유 패널을 **전수로** 열어 `[패널 → 텍스트 요소 → INTEGRATED/OVERLAY]` 원장을 남기게 하고, 1차 통과 후에도 텍스트 패널만 모아 나란히 비교하는 2차 스윕을 강제한다. EP01에서 13장이 "철자는 맞는데 후처리 룩"으로 새어 나간 뒤에 추가된 절차라고 적혀 있다.

프롬프트에 넣는 문구는 이렇다.

```
hand-lettered into the artwork in the same bold black comic ink as the linework,
integrated with the drawing (NOT a flat typeset/digital-font label pasted on top)
```

깨짐을 줄이는 요령도 정리돼 있다. 말풍선당 어절 수를 적게 끊고, 긴 대사는 여러 풍선이나 여러 패널로 나누고, 대본 원문 철자를 따옴표로 정확히 명시하고, 한 패널의 말풍선은 1~2개로 제한한다.

### 5-2. 실측 결과와 유보

두 번의 렌더 모두 한글이 정확했다. "신호가 또 늘었어요", "이건 사람이 놓친 신호예요" 모두 오탈자 없이 읽힌다. 어절 수가 적은 짧은 대사라는 조건에서다.

다만 정직하게 적으면, **두 장 모두 하네스 자신의 C3(d) 기준으로는 OVERLAY 판정을 받을 만하다.** 획이 균일하고 자간이 고르고 시스템 고딕에 가까운 룩이다. 손그림 잉크 톤을 프롬프트로 요구했는데도 그렇다. 카드뉴스라면 오히려 이 깔끔한 쪽이 읽기 좋을 수 있으니, 우리에게는 결함이라기보다 선택지의 문제다.

### 5-3. 우리가 고를 수 있는 세 번째 길

하네스는 오버레이를 금지하지만, 정작 저장소의 뷰어 템플릿에는 **CSS 말풍선 오버레이 렌더러가 통째로 살아 있다.** 대사·생각·외침·나레이션 4종의 말풍선 스타일과 꼬리 방향(left/right/up/down) 삼각형이 CSS로 구현돼 있고, `word-break: keep-all`로 한국어 어절 끊김까지 막아 두었다. 데이터 배열은 이렇게 생겼다.

```js
{ type: "dialogue", text: "이건 대사 말풍선.", x: 32, y: 70, w: 42, tail: "down" }
```

방침을 in-image 베이크로 바꾸면서 코드만 남은 것으로 보인다. 우리에게는 이게 오히려 쓸모가 있다. **그림은 codex로 생성하고, 한글 말풍선은 HTML/CSS로 얹는 혼합 방식**이 가능하다. 그러면 글자 깨짐 위험이 0이 되고, 대사 수정에 재렌더가 필요 없고, Pretendard를 그대로 쓸 수 있다. 대가는 하네스가 말한 "후작업 티"다.

카드뉴스는 원래 글자가 또렷한 매체이니, 우리 용도에서는 이 대가가 크지 않다고 본다. 판단은 사용자 몫이다.

## 7. 우리가 놓친 접근

`webtoon/cut01.png`과 `scripts/make_webtoon.py`를 다시 열어 하네스와 대조했다. 사용자가 "생각한 것과 많이 다르다"고 한 이유를 다섯 가지로 좁힐 수 있다.

**하나. 그림의 종류가 다르다.** 우리는 인물을 인라인 SVG로 그렸다. 타원 얼굴, 선 두 개의 눈, 곡선 하나의 입이다. 결과는 웹툰이 아니라 인포그래픽 아이콘이고, 6컷 모두 인물이 정면으로 서 있는 같은 구도다. 하네스는 처음부터 생성 이미지를 전제하고 그 대신 일관성을 통제하는 장치를 쌓았다. 우리는 일관성을 확실히 잡으려다 그림을 포기했다. §3-2와 §4-2의 실측이 보여주듯, **이제는 둘 다 가질 수 있다.**

**둘. 연출이 없다.** 하네스는 패널마다 size, camera, composition, emotion, motion을 지정한다. 클로즈업으로 감정에 진입하고, 반전은 단독 대형 컷으로 터뜨리고, 여백으로 시간을 조절한다. 우리 6컷은 전부 같은 크기, 같은 거리, 같은 정면 앵글이다. 카드뉴스라도 클로즈업 한 컷과 넓은 컷 한 컷의 대비는 있어야 읽는 맛이 생긴다.

**셋. 대본을 먼저 쓰지 않았다.** 하네스는 9명이 컨셉에서 대본까지 만든 다음에야 그림으로 넘어간다. 우리는 파이썬 파일 안에서 문구와 레이아웃과 SVG가 한꺼번에 태어났다. 그래서 "글이 먼저 좋은가"를 따로 검토할 기회가 없었다.

**넷. 스타일을 문서로 확정하지 않았다.** 발표자료의 색 토큰을 그대로 가져온 것은 좋았지만, 화풍·톤·인물 외형·말풍선 규약을 적어 놓은 문서가 없다. 다시 만들 때 기준으로 삼을 것이 남지 않았다.

**다섯. 검증 단계가 없다.** 만들고 바로 보여줬다. 하네스는 만든 에이전트와 검증하는 에이전트를 분리하고, 미달분을 되돌려 다시 만든다. 우리도 "컷을 열어 보고 기준 미달이면 다시"라는 루프를 한 번은 돌았어야 한다.

한편 우리 접근이 이긴 부분도 있다. 한글이 깨질 구조적 위험이 0이었고, 색이 발표자료와 정확히 일치했고, 컷당 생성 비용이 없었다. 이건 버릴 이유가 없다.

## 8. PharmaSignal 카드뉴스에 대한 제안

위를 종합하면 다음 조합을 제안한다. 아직 실행하지 않은 계획이므로 확정 사항이 아니다.

**단계 1. 대본 먼저.** 6~8컷의 컷별 대사와 비트를 마크다운 한 장으로 쓴다. 컷마다 `size / camera / emotion / 대사`를 적는다. 어휘는 `composition-grammar.md`에서 고른다.

**단계 2. 스타일과 인물 확정.** 화풍(셀 셰이딩 한국 웹툰), 팔레트(발표자료 토큰 유지), 인물 불변 토큰, 장소 토큰 2~3개를 한 문서로 적는다. 그 다음 기준 인물 컷 1장을 codex로 렌더해 확정한다.

**단계 3. 나머지 컷을 참조 파생으로.** 확정된 기준 컷을 `codex exec -i`로 붙여 나머지를 파생시킨다. 컷당 1회, 마음에 안 들면 그 컷만 다시. 6컷이면 codex 세션 6~12회 규모이고 유료 API 키는 필요 없다.

**단계 4. 한글은 오버레이로 얹기를 권한다.** `viewer-template.html`의 말풍선 CSS를 가져와 Pretendard로 얹는다. 이유는 세 가지다. 대사 수정에 재렌더가 필요 없고, 글자 깨짐 위험이 사라지고, 발표자료와 서체가 일치한다. 대신 렌더 프롬프트에서는 말풍선 자리를 여백으로 비워 두게 지시한다. 베이크 쪽이 웹툰답다는 반론이 있으니, 기준 컷 1장을 두 방식으로 만들어 보고 고르는 편이 낫겠다.

**단계 5. 검증 루프 한 바퀴.** 컷을 전부 열어 인물 동일성, 배경 연속성, 대사 흐름, 잘림·겹침을 본다. 미달 컷만 다시 만든다. 상한은 컷당 3회로 둔다.

기존 자산 중 살릴 것은 1080x1350 규격, 발표자료 색 토큰, 헤드리스 크롬 캡처 파이프라인, Pretendard 폰트 로딩이다. `make_webtoon.py`에서 SVG 인물 함수만 걷어내고 배경에 생성 이미지를 깔면 나머지 구조는 그대로 쓸 수 있다.

## 9. 확인하지 못한 것

- **무료 ChatGPT 플랜에서도 `image_generation`이 열리는지.** 이 환경은 이미 로그인돼 있었고 플랜 종류는 조회하지 않았다. [Gap:Assumption]
- **50장 규모 배치의 실제 소요·한도.** 저장소가 밝힌 5장 158초는 저장소 주장이고 우리가 재현하지 않았다. 우리는 단발 2장만 돌렸으며 렌더 시각을 따로 재지 않았다. [Gap:Procedural]
- **하네스 전체를 돌린 결과물.** 저장소에 예제 출력이 없고(`.gitignore`로 제외) 우리도 실행하지 않았다. 27개 에이전트 협업이 실제로 어떤 품질을 내는지는 문서 기준의 추정이다. [Gap:Procedural]
- **`codex exec -i`의 참조 보존 강도.** 2장 사이에서는 잘 유지됐지만, 6~8컷으로 늘렸을 때 얼마나 흔들리는지는 재보지 않았다. [Gap:Procedural]
- **codex 배치 헬퍼 스크립트.** 저장소가 참조하는 `codex_imagegen_batch.sh`는 포함돼 있지 않고 우리 로컬에도 없다. 병렬이 필요하면 직접 작성해야 한다. [Gap:Consideration]
